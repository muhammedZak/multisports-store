# MultiSports Store Codebase Overview

This document is a top-to-bottom walkthrough of the repository as it exists now. It is based on the checked-out source, not only on the root `README.md`.

> **Important repository-state note:** the root `README.md` still says that no business feature has been implemented. That description is stale. The source currently includes authentication, customer profiles and addresses, category/product catalog management, product images and variants, public catalog pages, and inventory management. There is no cart, checkout, order, payment, review, or wishlist module yet.

## 1. Root level

### What lives at the root

| Path | Purpose |
| --- | --- |
| `package.json` | Workspace-level development commands. Its only dependency is `concurrently`, used to run the two applications together. |
| `package-lock.json` | Locks the root dependency tree. |
| `.gitignore` | Excludes dependencies, local `.env` files, Vite output, logs, OS files, and editor settings. It explicitly allows `.env.example` files. |
| `README.md` | An older setup-phase checklist; its project-state claims no longer match the implemented source. |
| `.git/` | Git's internal repository metadata; not application code. |
| `client/` | React 19 single-page application built with Vite, React Router, Redux Toolkit, Axios, and Tailwind CSS. |
| `server/` | Express 5 API, Mongoose data layer, session authentication, uploads, and external-service integrations. |
| `node_modules/` | Installed root dependencies; generated by npm and ignored by Git. |

The root, `client/`, and `server/` each have their own `node_modules/` because they have separate package manifests. These are generated dependency trees, not source. The working tree also contains `client/dist/` and `client/dist/assets/`, the generated Vite production build and its bundled assets. They are ignored by Git and are not application source.

### Root scripts and how both applications start

`package.json` delegates work to each subproject with npm's `--prefix` flag:

```json
// package.json
{
  "scripts": {
    "dev": "concurrently \"npm run dev --prefix client\" \"npm run dev --prefix server\"",
    "dev:client": "npm run dev --prefix client",
    "dev:server": "npm run dev --prefix server",
    "build": "npm run build --prefix client",
    "lint": "npm run lint --prefix client"
  }
}
```

- `npm run dev` starts Vite and Nodemon as two child processes in one terminal. `concurrently` prefixes/interleaves their output and keeps both running.
- `npm run dev:client` starts only the React/Vite application.
- `npm run dev:server` starts only the Node API.
- `npm run build` creates the client production bundle in `client/dist/`.
- `npm run lint` runs ESLint only for the client. There is no server lint script.

The delegated scripts are:

```json
// client/package.json
"dev": "vite",
"build": "vite build",
"lint": "eslint .",
"preview": "vite preview"

// server/package.json
"dev": "nodemon src/server.js",
"start": "node src/server.js",
"inventory:bootstrap": "node src/scripts/bootstrapInventory.js"
```

Nodemon restarts the server when server files change; Vite serves the React app with hot module replacement. The example configuration uses client port `5173` and API port `5000`. `env.js` itself falls back to API port `4000` if `PORT` is absent, so the example's `PORT=5000` is what aligns normal local development with `VITE_API_BASE_URL`.

### Environment setup

There are separate local environment files for browser-safe and server-secret values. Both `server/.env` and `client/.env` are present locally, but their values are intentionally not reproduced here. They are ignored by Git. Safe templates live in `server/.env.example` and `client/.env.example`.

```dotenv
# client/.env.example
VITE_API_BASE_URL=http://localhost:5000/api/v1
VITE_GOOGLE_CLIENT_ID=
```

Vite exposes only variables whose names begin with `VITE_`, so these values are visible to browser code. `VITE_API_BASE_URL` becomes the prefix for every Axios request. `VITE_GOOGLE_CLIENT_ID` is used when Google Identity Services is initialized; it is an identifier, not a secret.

```dotenv
# server/.env.example
NODE_ENV=development
PORT=5000
MONGODB_URI=mongodb://127.0.0.1:27017/multisports_store
CLIENT_ORIGINS=http://localhost:5173
LOW_STOCK_THRESHOLD=5
SESSION_SECRET=replace_with_a_long_random_secret
AUTH_CHALLENGE_SECRET=replace_with_a_different_long_random_secret
RESEND_API_KEY=
RESEND_FROM_EMAIL=
GOOGLE_CLIENT_ID=
CLOUDINARY_CLOUD_NAME=
CLOUDINARY_API_KEY=
CLOUDINARY_API_SECRET=
```

| Server variable | Meaning and validation |
| --- | --- |
| `NODE_ENV` | `development`, `test`, or `production`; defaults to `development`. Controls request logging, secure cookies, and production error detail. |
| `PORT` | Positive integer; defaults to `4000` in code. |
| `MONGODB_URI` | Required MongoDB connection URI, used by Mongoose and the session store. |
| `CLIENT_ORIGINS` | Required comma-separated browser origins accepted by CORS. |
| `LOW_STOCK_THRESHOLD` | Non-negative integer; defaults to `5`. Inventory at or below it is classified as low stock unless quantity is zero. |
| `SESSION_SECRET` | Required, at least 32 characters; signs the session cookie. |
| `AUTH_CHALLENGE_SECRET` | Required, at least 32 characters; participates in hashing OTP challenges. |
| `RESEND_API_KEY`, `RESEND_FROM_EMAIL` | Both required at startup for email verification/login/reset/change messages. Blank example values must be replaced. |
| `GOOGLE_CLIENT_ID` | Required at startup; verifies Google ID-token audiences. |
| `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` | All required at startup for profile and product image operations. |

The fail-fast checks are centralized:

```js
// server/src/config/env.js
if (!process.env.MONGODB_URI) {
  throw new Error('MONGODB_URI is required');
}

if (!process.env.SESSION_SECRET || process.env.SESSION_SECRET.length < 32) {
  throw new Error('SESSION_SECRET must contain at least 32 characters');
}

export const env = Object.freeze({
  nodeEnv,
  port,
  lowStockThreshold,
  mongodbUri: process.env.MONGODB_URI,
  clientOrigins,
  // ...secrets and integration configuration
});
```

Because importing `env.js` runs these checks, the server will not finish starting if any required integration setting is blank, even if that integration is not used immediately.

## 2. Server folder

### Server folder map

The server uses **feature modules**, rather than top-level `routes/`, `controllers/`, and `models/` folders. Each business area keeps its route, controller, service, validation, and model files together.

```text
server/
|-- package.json                 Server dependencies and scripts
|-- package-lock.json            Locked server dependency tree
|-- .env                         Local secrets/configuration (ignored)
|-- .env.example                 Safe configuration template
|-- node_modules/                Generated installed server dependencies
`-- src/
    |-- server.js                Process entry point
    |-- app.js                   Express application composition
    |-- config/                  Environment, database, CORS, sessions
    |-- integrations/            Cloudinary, Google, and Resend adapters
    |-- middleware/              Authentication, CSRF, 404, error handling
    |-- modules/
    |   |-- auth/                Sessions, password/OTP/Google auth
    |   |-- users/               Customer profile, photo, and addresses
    |   |-- catalog/             Sports, categories, products, media, variants
    |   `-- inventory/           Stock positions and adjustment history
    |-- scripts/                 One-off executable maintenance scripts
    `-- utils/                   Shared AppError class
```

There are no empty folders under `server/src/`. There is no test folder and no test script in `server/package.json`.

### Entry point and startup sequence

`server/src/server.js` is the executable entry point. It waits for MongoDB before opening a network port, so the API never reports itself as running with an unavailable initial database connection.

```js
// server/src/server.js
async function startServer() {
  try {
    await connectDatabase();
    const httpServer = createServer(app);

    httpServer.listen(env.port, () => {
      console.log(`Server running on http://localhost:${env.port}`);
    });
  } catch (error) {
    console.error('Failed to start server:', error.message);
    process.exit(1);
  }
}
```

`connectDatabase()` calls `mongoose.connect()` with the configured URI and a five-second initial server-selection timeout:

```js
// server/src/config/database.js
export async function connectDatabase() {
  await mongoose.connect(env.mongodbUri, {
    serverSelectionTimeoutMS: 5000,
  });
  console.log('MongoDB connected');
}
```

### Express application and middleware order

`server/src/app.js` creates and exports the Express application. Middleware order matters:

1. `helmet()` adds common security-related response headers.
2. `cors(corsOptions)` accepts requests without an `Origin` header or from a configured client origin and allows credentials.
3. `morgan('dev')` logs requests only in development.
4. `express.json()` and `express.urlencoded()` parse JSON and form bodies.
5. `sessionMiddleware` loads/saves the MongoDB-backed browser session.
6. The health and feature routers handle known endpoints.
7. `notFoundHandler` converts unmatched requests into an `AppError`.
8. `errorHandler` produces the common JSON error response.

```js
// server/src/app.js
app.use(helmet());
app.use(cors(corsOptions));
if (env.nodeEnv === 'development') app.use(morgan('dev'));
app.use(express.json());
app.use(express.urlencoded({ extended: true }));
app.use(sessionMiddleware);

app.get('/api/v1/health', /* inline handler */);
app.use('/api/v1/auth', authRouter);
app.use('/api/v1/users', userRouter);
app.use('/api/v1', categoryRouter);
app.use('/api/v1', publicCatalogRouter);
app.use('/api/v1/admin/categories', adminCategoryRouter);
app.use('/api/v1/admin/products', adminProductRouter);
app.use('/api/v1/admin/inventory', adminInventoryRouter);

app.use(notFoundHandler);
app.use(errorHandler);
```

Express 5 handles rejected promises from these async controllers and forwards them to the error middleware. The project therefore does not wrap every controller in a custom async-error helper.

### Sessions, CORS, authentication, and CSRF

Sessions are persisted in MongoDB's `sessions` collection by `connect-mongo`. The browser receives a `multisports.sid` cookie that is HTTP-only, `SameSite=Lax`, lasts seven days, and is marked secure in production.

```js
// server/src/config/session.js
export const sessionMiddleware = session({
  name: 'multisports.sid',
  secret: env.sessionSecret,
  resave: false,
  saveUninitialized: false,
  store: MongoStore.create({
    mongoUrl: env.mongodbUri,
    collectionName: 'sessions',
    ttl: SESSION_MAX_AGE_MS / 1000,
  }),
  cookie: { httpOnly: true, secure: env.nodeEnv === 'production', sameSite: 'lax' }
});
```

`requireAuth` resolves `req.session.userId` to a current user and puts the safe user resource on `req.user`. `requireCustomer` and `requireAdmin` enforce its `role`. `requireRecentAuthentication` additionally restricts the start of an email change to a login performed within ten minutes.

CSRF tokens are random, stored in the server-side session, kept in client memory, and sent as `X-CSRF-Token` on unsafe requests. Authentication registration/email-verification endpoints are rate-limited but sit before the auth router's blanket CSRF middleware. Login, Google auth, OTP login, password recovery/reset, email changes, logout, and protected business mutations require the token.

### Responsibilities inside a feature module

The recurring server flow is:

```text
*.routes.js -> *.controller.js -> *.validation.js + *.service.js -> *.model.js
```

- `*.routes.js` chooses the URL, HTTP method, access guards, upload middleware, and controller.
- `*.controller.js` translates Express `req` data into validated service arguments, chooses the HTTP status, and shapes the JSON envelope.
- `*.validation.js` validates body/query values and throws structured `AppError` instances for bad input.
- `*.service.js` contains business rules, database reads/writes, resource mapping, and external integration calls.
- `*.model.js` defines persistence shape, indexes, schema-level validation, and relationships.
- `*.constants.js` stores shared enums such as sports, stock states, and adjustment reasons.

Other notable folders/files:

- `integrations/cloudinary.js` uploads/deletes profile photos and product images in separate Cloudinary folders.
- `integrations/google.js` verifies a Google ID token and returns its subject, verified email, and name.
- `integrations/resend.js` sends the four OTP email types.
- `middleware/error.middleware.js` returns `{ success: false, error: { code, message, fields? } }`; production hides internal 500 messages.
- `modules/auth/auth.challenge.js` generates and hashes OTPs; `auth.session.js` regenerates sessions and manages short-lived password-reset authorization; `auth.rateLimit.js` defines auth rate limiters.
- `modules/catalog/product.upload.js` and `modules/users/profilePhoto.upload.js` use Multer memory storage and accept JPEG/PNG/WebP files up to 5 MB.
- `scripts/bootstrapInventory.js`, run via `npm run inventory:bootstrap --prefix server`, creates missing zero-quantity inventory positions for existing catalog records and then disconnects from MongoDB.
- `utils/AppError.js` carries HTTP status, stable error code, message, and optional per-field errors.

## 3. MongoDB Models

Six explicit Mongoose models exist. `Order` does **not** exist yet. Session documents are also stored in MongoDB by `connect-mongo`, but they are not defined as a project Mongoose model.

### Relationship map

```text
Category 1 <---- many Product
                     |
                     | Product._id / embedded variant._id
                     v
                 Inventory 1 <---- many InventoryAdjustment
                                           |
                                           `---- optional User (performedBy)

User 1 <---- many AuthChallenge
 |
 `---- embedded addresses and optional embedded profilePhoto
```

### `User` — `server/src/modules/users/user.model.js`

Represents either a customer or an administrator.

| Field | Type | Meaning / rules |
| --- | --- | --- |
| `name` | `String` | Required display/name value; whitespace trimmed. |
| `email` | `String` | Required, trimmed, lowercased, email-pattern validated, and unique through an index. |
| `googleSub` | `String` | Optional Google account subject. Excluded from ordinary queries with `select: false`; unique only when it is a string. |
| `role` | `String` | Required enum: `customer` or `admin`; defaults to `customer`. |
| `passwordHash` | `String` | Optional Argon2 hash; excluded from ordinary queries. A Google-only account may not have one. |
| `emailVerified` | `Boolean` | Required; defaults to `false`. |
| `phone` | `String` | Optional, trimmed; permits common formatting and requires 7–15 digits with maximum total length 25. |
| `profilePhoto` | Embedded object | Optional `{ publicId, url }`; both strings are required when the object exists. It has no separate `_id`. |
| `addresses` | Embedded object array | Defaults to `[]`; each address gets its own Mongoose `_id`, used as `addressId` by address endpoints. |
| `createdAt`, `updatedAt` | `Date` | Added automatically by `timestamps: true`. |

Each embedded address has required trimmed strings `fullName`, `phone`, `address`, `city`, `state`, `postalCode`, and `country`, plus required Boolean `isDefault` (default `false`). Length and phone validation are applied in the schema. Addresses are owned by the user document; there is no separate `Address` collection.

```js
// server/src/modules/users/user.model.js
const userSchema = new mongoose.Schema({
  email: { type: String, required: true, trim: true, lowercase: true },
  role: { type: String, enum: ['customer', 'admin'], default: 'customer' },
  passwordHash: { type: String, select: false },
  profilePhoto: { type: profilePhotoSchema, default: undefined },
  addresses: { type: [addressSchema], default: [] }
}, { timestamps: true });
```

### `AuthChallenge` — `server/src/modules/auth/authChallenge.model.js`

Stores a hashed, expiring OTP-like authentication challenge.

| Field | Type | Meaning / rules |
| --- | --- | --- |
| `userId` | `ObjectId`, ref `User` | Required owner of the challenge. |
| `targetEmail` | `String` | Required normalized email that receives/is verified by the challenge. |
| `purpose` | `String` | Required enum: `email_verification`, `otp_login`, `password_reset`, or `email_change`. |
| `challengeHash` | `String` | Required hash; excluded from normal query results. The raw OTP is not stored. |
| `expiresAt` | `Date` | Required expiry time. A TTL index asks MongoDB to remove expired documents. |
| `usedAt` | `Date` or `null` | Marks consumption; defaults to `null`. |
| `attemptCount` | `Number` | Required non-negative counter; defaults to `0`. |
| `lastSentAt` | `Date` or `null` | Supports resend cooldown; defaults to `null`. |
| `createdAt`, `updatedAt` | `Date` | Automatic timestamps. |

The compound unique index `{ userId, purpose }` permits at most one challenge of a given purpose per user.

### `Category` — `server/src/modules/catalog/category.model.js`

| Field | Type | Meaning / rules |
| --- | --- | --- |
| `name` | `String` | Required trimmed display name. |
| `nameKey` | `String` | Required normalized name used for case/format-insensitive uniqueness. |
| `sport` | `String` | Required enum: `football`, `cricket`, `basketball`, `tennis`, `badminton`, `running`, or `fitness`. |
| `isActive` | `Boolean` | Required publication/availability flag. |
| `createdAt`, `updatedAt` | `Date` | Automatic timestamps. |

The unique `{ sport, nameKey }` index means two sports may reuse a category name, but the same normalized name cannot be repeated within one sport.

### `Product` — `server/src/modules/catalog/product.model.js`

| Field | Type | Meaning / rules |
| --- | --- | --- |
| `name` | `String` | Required trimmed product name. |
| `description` | `String` | Required trimmed description. |
| `brand` | `String` | Required trimmed brand. |
| `sport` | `String` | Required supported-sport enum. Services also ensure it matches the category's sport. |
| `categoryId` | `ObjectId`, ref `Category` | Required category relationship. Services populate it for API resources. |
| `images` | Embedded object array | Required and non-empty; at most one image may be primary. Each image has an `_id`, required Cloudinary `publicId`/`url`, optional `altText` defaulting to `''`, Boolean `isPrimary`, and non-negative integer `sortOrder`. |
| `variants` | Embedded object array | Defaults to `[]`. Each variant has its own `_id`, required `options` object and required `isActive`. Options must contain at least one non-empty string pair, for example `{ size: "M", color: "Blue" }`. |
| `basePrice` | `Number` | Required positive integer stored in **paise**, not a floating-point rupee amount. |
| `discountType` | `String` or `null` | `percentage`, `fixed`, or `null`; defaults to `null`. |
| `discountValue` | `Number` or `null` | Integer when a discount exists. Percentages are 1–100; fixed discounts are positive paise below `basePrice`; must be `null` when type is `null`. |
| `specifications` | `Mixed` object | Defaults to `{}`; values may only be finite numbers, strings, or Booleans. |
| `isActive` | `Boolean` | Required publication flag. |
| `createdAt`, `updatedAt` | `Date` | Automatic timestamps. |

```js
// server/src/modules/catalog/product.model.js
categoryId: {
  type: mongoose.Schema.Types.ObjectId,
  ref: 'Category',
  required: true,
},
basePrice: {
  type: Number,
  required: true,
  min: 1,
  validate: { validator: Number.isInteger }
}
```

Indexes support weighted text search (`name` weight 10, `brand` weight 5) and active catalog filtering by sport, category, and creation time.

### `Inventory` — `server/src/modules/inventory/inventory.model.js`

Represents one stock position.

| Field | Type | Meaning / rules |
| --- | --- | --- |
| `productId` | `ObjectId`, ref `Product` | Required product relationship. |
| `variantId` | `ObjectId` or omitted | For a variant product, matches an embedded `Product.variants._id`. For a simple product it must be omitted, not `null`. It is intentionally not a Mongoose `ref` because variants are embedded rather than a collection. |
| `quantity` | `Number` | Required non-negative integer. |
| `createdAt`, `updatedAt` | `Date` | Automatic timestamps. |

The unique `{ productId, variantId }` index prevents duplicate stock positions. A separate quantity index supports stock-state filtering. Stock state is derived rather than stored: zero is `out_of_stock`, values up to `LOW_STOCK_THRESHOLD` are `low_stock`, and larger values are `in_stock`.

### `InventoryAdjustment` — `server/src/modules/inventory/inventoryAdjustment.model.js`

An immutable-style audit record describing a change to one inventory position.

| Field | Type | Meaning / rules |
| --- | --- | --- |
| `inventoryId` | `ObjectId`, ref `Inventory` | Required inventory relationship. |
| `reason` | `String` | Required enum: `initial_stock`, `restock`, `manual_correction`, `order_purchase`, `order_cancellation`, or `refund_return`. Current admin manual adjustments allow `restock` and `manual_correction`. |
| `quantityChange` | `Number` | Required non-zero integer; positive adds stock and negative removes it. |
| `previousQuantity` | `Number` | Required non-negative integer. |
| `newQuantity` | `Number` | Required non-negative integer and must equal `previousQuantity + quantityChange`. |
| `performedBy` | `ObjectId`, ref `User`, or omitted | Optional actor; manual admin changes set this from `req.user.id`. |
| `sourceType` | `String` or omitted | Optional source label. Must be provided together with `sourceId`. |
| `sourceId` | `ObjectId` or omitted | Optional source-document ID. Must be provided together with `sourceType`. No fixed `ref`, allowing future source types such as orders. |
| `note` | `String` or omitted | Optional trimmed note; required for `manual_correction`. |
| `createdAt`, `updatedAt` | `Date` | Automatic timestamps. |

Its MongoDB collection name is explicitly `inventoryAdjustments`. Indexes optimize an inventory's newest-first history and optional source lookup.

## 4. API Routes

All endpoints are under `/api/v1`. Successful JSON responses consistently begin with `success: true`; list responses generally place pagination in top-level `meta`. Controllers validate input and delegate business/database work to services.

Security shorthand below:

- **Public**: no authenticated user required.
- **Session**: uses the session if one exists.
- **Customer/Admin**: requires that role.
- **CSRF**: requires the session token in `X-CSRF-Token`.
- Auth endpoints also apply the rate limiter shown in their route file.

### System

| Method | Path | Purpose | Handler |
| --- | --- | --- | --- |
| GET | `/api/v1/health` | Return `{ status: "ok" }` to prove the Express process is responding. It does not perform a fresh DB query. | Inline handler in `server/src/app.js` |

Route ordering is significant:

```js
router.post('/email-verification/resend', resendVerificationRateLimiter, resendVerificationEmail);

router.use(requireCsrf);

router.post('/login', loginRateLimiter, login);
// all routes declared below inherit CSRF protection
```

### Public sports and categories

### Shared Axios instance and API helpers

All endpoint modules import one Axios instance:

```js
// client/src/api/client.js
export const apiClient = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL,
  withCredentials: true,
});

apiClient.interceptors.request.use((config) => {
  const method = config.method?.toLowerCase();
  if (method && !SAFE_METHODS.has(method)) {
    const csrfToken = getCsrfToken();
    if (csrfToken) config.headers['X-CSRF-Token'] = csrfToken;
  }
  return config;
});
```

`withCredentials: true` allows the browser to send/receive the session cookie across the Vite/API origins. `api/csrf.js` keeps the token in module memory; the interceptor adds it to POST/PUT/PATCH/DELETE requests. Refreshing the page clears that memory, so `bootstrapAuth` first calls `/auth/csrf-token` and restores it.

The API modules isolate URL and response-envelope knowledge from UI components:

| File | API area |
| --- | --- |
| `api/authApi.js` | CSRF/session, registration, verification, password/OTP/Google authentication, recovery, password/email changes, logout. |
| `api/userApi.js` | Customer profile/photo and embedded address CRUD/default operations. |
| `api/categoryApi.js` | Sports, public categories, and admin category management. |
| `api/productApi.js` | Public catalog/detail/filter options and admin product/media/variant management. |
| `api/inventoryApi.js` | Admin inventory list/detail/manual adjustment/history. |
| `api/errors.js` | Converts Axios errors to stable `{ code, message, fields }` objects for pages. |

For example, UI code does not need to know the response nesting:

```js
// client/src/api/productApi.js
export async function fetchPublicProduct(productId) {
  const response = await apiClient.get(`/products/${productId}`);
  return response.data.data.product;
}
```

## 6. Data Flow

### Complete example: opening a public product details page

This trace uses real files and follows `GET /api/v1/products/:productId` from the browser to MongoDB and back.

#### 1. React routing supplies the product ID

`client/src/app/router/AppRouter.jsx` maps the browser URL to the page:

```jsx
<Route path='/products/:productId' element={<ProductDetailsPage />} />
```

`client/src/pages/storefront/ProductDetailsPage.jsx` reads that parameter. Its effect runs `loadProduct()` on first render and whenever the ID changes:

```jsx
const { productId } = useParams();

const loadProduct = useCallback(async () => {
  setLoading(true);
  setError(null);

  try {
    const item = await fetchPublicProduct(productId);
    setProduct(item);
    // choose primary/first image and reset variant selection
  } catch (requestError) {
    setError(normalizeApiError(requestError, 'Unable to load this product.'));
  } finally {
    setLoading(false);
  }
}, [productId]);

useEffect(() => { loadProduct(); }, [loadProduct]);
```

The page initially renders a loading state. Later it renders product data or a normalized error (including a special not-found view for `PRODUCT_NOT_FOUND`).

#### 2. The API helper calls shared Axios

`client/src/api/productApi.js` calls a relative path:

```js
const response = await apiClient.get(`/products/${productId}`);
return response.data.data.product;
```

`client/src/api/client.js` prefixes it with `VITE_API_BASE_URL`, normally producing:

```text
GET http://localhost:5000/api/v1/products/<productId>
```

Axios has `withCredentials: true`, although this public GET does not require a login. GET is a safe method, so the request interceptor does not attach a CSRF header.

#### 3. Express receives and routes the request

The request passes through Helmet, CORS, development logging, body parsers, and session loading in `server/src/app.js`. That file mounts `publicCatalogRouter` at `/api/v1`:

```js
app.use('/api/v1', publicCatalogRouter);
```

`server/src/modules/catalog/publicCatalog.routes.js` matches the remainder and selects the controller:

```js
router.get('/products/:productId', getProductForPublic);
```

No auth or CSRF middleware is attached to this route.

#### 4. The controller delegates and shapes the HTTP response

`server/src/modules/catalog/product.controller.js` passes the URL parameter to the service and wraps the result:

```js
export async function getProductForPublic(req, res) {
  const product = await getPublicProduct(req.params.productId);

  res.status(200).json({
    success: true,
    data: { product },
  });
}
```

#### 5. The service reads MongoDB and enforces public visibility

`server/src/modules/catalog/product.service.js` first rejects a malformed MongoDB ID. It then queries the `products` collection for that ID **and** `isActive: true`, selects only public fields, and populates `categoryId` from the `categories` collection:

```js
const product = await Product.findOne({
  _id: productId,
  isActive: true,
})
  .select('name description brand sport categoryId images variants basePrice discountType discountValue specifications')
  .populate('categoryId', 'name sport isActive')
  .lean();
```

It deliberately returns not found when the category is missing/inactive or its sport does not match the product. This prevents inactive catalog data from leaking through the public endpoint.

Next, `getPublicProductAvailabilities([product])` in `server/src/modules/inventory/inventory.service.js` performs one query against `inventories`:

```js
const inventories = await Inventory.find({
  productId: { $in: productIds },
})
  .select('productId variantId quantity')
  .lean();
```

For a simple product it derives one stock state from its position. For a variant product it derives each active variant's state and rolls them up to the product: any in-stock active variant makes the product in stock; otherwise any low-stock variant makes it low stock; otherwise it is out of stock.

Finally, `toPublicProductResource(product, availability)` maps MongoDB details into the API resource: ObjectIds become string `id` values, prices/discount data are shaped for the UI, images are ordered, inactive variants are removed, and stock states are included.

#### 6. The response travels back to the UI

The controller returns HTTP 200:

```json
{
  "success": true,
  "data": {
    "product": {
      "id": "...",
      "name": "...",
      "category": { "id": "...", "name": "..." },
      "images": [],
      "stockState": "in_stock",
      "variants": []
    }
  }
}
```

Axios resolves the promise, `fetchPublicProduct` unwraps `data.product`, and `ProductDetailsPage` stores it with `setProduct`. React re-renders the image gallery, name/brand/category, INR price and discount, stock label, active variants, and specifications.

If any service throws `AppError`—for example `PRODUCT_NOT_FOUND`—Express 5 forwards it to `server/src/middleware/error.middleware.js`. Axios rejects; the page's catch block calls `normalizeApiError`; React then shows the appropriate error state. Unexpected production errors are returned as a generic message.

### Where to add a new feature

Use the existing vertical-module pattern:

1. **Persistence:** add or extend a schema within the relevant `server/src/modules/<feature>/` directory. Create a new module if the concept is independent (for example `orders/`). Add explicit `ObjectId` refs only for separate collections; use subdocuments for data owned entirely by one parent.
2. **Business logic:** put database operations and rules in `<feature>.service.js`, not in routes or React pages.
3. **Input boundary:** add body/query validation in `<feature>.validation.js`.
4. **HTTP boundary:** add a small controller in `<feature>.controller.js`, then declare the endpoint and its auth/role/CSRF/upload middleware in `<feature>.routes.js`.
5. **Mounting:** if it is a new router, import and mount it in `server/src/app.js` before the 404 and error middleware.
6. **Client transport:** add a function to the matching `client/src/api/*Api.js` module (or a new one). Keep base URL, cookies, and CSRF behavior in the shared `apiClient`.
7. **UI:** add reusable feature components under `client/src/features/<feature>/`, full screens under the correct `client/src/pages/` area, and browser routes/guards in `client/src/app/router/AppRouter.jsx`.
8. **Shared state:** use page-local state for screen-only data. Add a Redux slice and register it in `client/src/app/store/store.js` only when state genuinely needs to be shared across distant screens or persisted through navigation.
9. **Configuration/integrations:** define and validate new server settings in `server/src/config/env.js`, add safe names to `.env.example`, and isolate third-party calls under `server/src/integrations/`.

That path preserves the project's established request flow:

```text
React page/component
  -> client API helper
  -> shared Axios instance
  -> Express route + middleware
  -> controller + validation
  -> service
  -> Mongoose model / integration
  -> standard JSON response
  -> page state and render
```
